## 7.1 โมเดลความปลอดภัยในประโยคเดียว

> **ปลั๊กอินของ Killian 2 ไม่ได้รันในแซนด์บ็อกซ์ — มันรันด้วยสิทธิ์เต็มของหน้าต่างโปรแกรม ผู้ใช้จึงต้อง "เชื่อผู้เขียน" และโปรแกรมช่วยแค่ให้การตัดสินใจนั้นเกิดขึ้นอย่างรู้ตัว**

ทั้งผู้ใช้และผู้เขียนควรเข้าใจข้อนี้ตรงกัน ระบบสิทธิ์แบบแอปมือถือ (ขออนุญาตทีละความสามารถ) **ยังไม่มี**

## 7.2 ปลั๊กอินทำอะไรได้จริง

| ความสามารถ | ผ่าน `k2` (ทางที่รองรับ) | ความจริงของสภาพแวดล้อม |
|---|---|---|
| อ่าน/เขียนไฟล์ | เฉพาะข้อความ · เฉพาะในโฟลเดอร์ผลงาน · ไม่มีลบ/ย้าย | โค้ดอยู่ในหน้าต่างเดียวกับโปรแกรม จึงเอื้อมถึงสะพานภายในของโปรแกรมได้ ซึ่งไม่ถูกจำกัดด้วยขอบเขตของ `k2` |
| เครือข่าย | `k2.fetch` ไปที่ใดก็ได้ | ไม่มีรายการโดเมนที่อนุญาตสำหรับปลั๊กอิน |
| หน้าจอ | แผง · คำสั่ง · กล่องถาม | แก้ DOM ของทั้งโปรแกรมได้ · ดักการกดแป้นได้ |
| เนื้อหาของผู้ใช้ | `getMarkdown` · `getEditorView` | อ่านทุกอย่างที่อยู่บนจอและในหน่วยความจำของหน้าต่างได้ |
| ข้อมูลในเครื่อง | — | อ่าน `localStorage` ของโปรแกรมและของปลั๊กอินอื่นได้ |

ข้อสรุปที่ตรงไปตรงมา:

- ขอบเขตของ `k2` (ทางสัมพัทธ์ · ห้าม `..` · ข้อความเท่านั้น) คือ **ราวกันตก ไม่ใช่กำแพง** — กันความผิดพลาดของผู้เขียนที่สุจริต ไม่ได้กันผู้เขียนที่ประสงค์ร้าย
- ผู้ใช้ควรปฏิบัติต่อการติดตั้งปลั๊กอินเหมือน **การติดตั้งโปรแกรมหนึ่งตัว**
- ปลั๊กอินที่ดีอยู่ในขอบเขตของ `k2` เท่านั้น — ตรวจได้จากการอ่านซอร์ส (ไฟล์เดียว เป็นข้อความ)

## 7.3 การอนุญาตปลั๊กอินของผลงาน

ปลั๊กอินมีสองที่ และถูกปฏิบัติต่างกัน:

| | ของผู้ใช้ (`<ข้อมูลผู้ใช้>/Plugins/`) | ของผลงาน (`<ผลงาน>/Plugins/`) |
|---|---|---|
| มาอยู่ได้ยังไง | ผู้ใช้ติดตั้งเอง (จากลิงก์ → ยืนยัน · หรือวางโฟลเดอร์เอง) | มากับโฟลเดอร์ผลงาน — **อาจมาจากคนอื่น** (zip · ซิงก์ · Git) |
| รันเมื่อ | เปิดผลงาน | **หลังผู้ใช้กดอนุญาตเท่านั้น** |

### กลไก

1. ตอนเปิดผลงาน โปรแกรมอ่าน `plugin.json` + ไฟล์ entry ของปลั๊กอิน **ทุกตัว** ใน `<ผลงาน>/Plugins/` แล้วคำนวณ **ลายนิ้วมือของทั้งชุด** (ชื่อโฟลเดอร์ + แฮชของ manifest + แฮชของโค้ด ของทุกตัว)
2. เทียบกับการอนุญาตที่เก็บไว้ **ในเครื่องของผู้ใช้** (`<ข้อมูลผู้ใช้>/sessions/` — ผูกกับทางของผลงาน)
3. ไม่ตรง → ทุกตัวในชุดเป็น **รออนุญาต** — **โค้ดไม่ถูกรันแม้แต่บรรทัดเดียว** · แถบสถานะแจ้งจำนวน · ไม่มีกล่องเด้งขวาง (กล่องที่โผล่เองตอนโหลดมักถูกกดผ่านโดยไม่อ่าน)
4. ผู้ใช้เปิดแผงปลั๊กอิน → **อนุญาตปลั๊กอินของโปรเจกต์นี้** → กล่องยืนยันอีกชั้น → โปรแกรมจดลายนิ้วมือปัจจุบัน → รัน

### สิ่งที่ตามมา

| สถานการณ์ | ผล |
|---|---|
| มีคนเพิ่ม/แก้/แทนที่ปลั๊กอินในโฟลเดอร์ผลงาน (ซิงก์ · แตกซิปทับ · `git pull`) | ลายนิ้วมือเปลี่ยน → **ต้องอนุญาตใหม่ทั้งชุด** |
| **คุณแก้ไฟล์เองระหว่างพัฒนา** | เช่นกัน — ทุกครั้งที่บันทึกไฟล์ → พัฒนาในโฟลเดอร์ของผู้ใช้สะดวกกว่า |
| ผู้ใช้ถอนปลั๊กอินตัวหนึ่งออกจากชุดที่อนุญาตแล้ว | ตัวที่เหลือได้รับอนุญาตต่อ (การเอาโค้ดออกไม่เพิ่มความเสี่ยง) |
| ย้ายโฟลเดอร์ผลงานไปที่อื่น / เปิดบนเครื่องอื่น | ต้องอนุญาตใหม่ (การอนุญาตผูกกับทางและเครื่อง) |
| ผู้ส่งผลงานแนบไฟล์ "อนุญาตแล้ว" มาในผลงาน | ไม่มีผล — การอนุญาตไม่ได้อยู่ในโฟลเดอร์ผลงาน |
| ไฟล์อื่นในโฟลเดอร์ปลั๊กอิน (ไม่ใช่ manifest/entry) เปลี่ยน | ลายนิ้วมือไม่เปลี่ยน — โปรแกรมรันแค่ไฟล์ entry และแฮชครอบโค้ดที่ถูกรันจริง |

ลายนิ้วมือใช้ตรวจว่า "เปลี่ยนไหม" (แฮชแบบเร็ว ไม่ใช่แฮชเข้ารหัส) — เป็นกลไกยืนยันความตั้งใจของผู้ใช้ ไม่ใช่ลายเซ็นดิจิทัลของผู้เขียน **ยังไม่มีการลงนามปลั๊กอิน**

### ผลต่อผู้เขียนที่แจกปลั๊กอินไปกับผลงาน

- บอกผู้รับในเอกสารของผลงานว่ามีปลั๊กอินอะไร ทำอะไร และต้องกดอนุญาตที่ไหน
- ปลั๊กอินต้องทนได้กับสภาพ "ยังไม่ถูกรัน" — ผลงานต้องเปิดและใช้ได้โดยไม่มีปลั๊กอิน
- อัปเดตปลั๊กอินในผลงาน = ทุกคนที่เปิดต้องอนุญาตใหม่

## 7.4 ข้อปฏิบัติของผู้เขียนปลั๊กอิน

### ขอบเขต

- [ ] ใช้เฉพาะ `k2` — **ไม่แตะตัวแปรภายในของโปรแกรมบน `window`** (เช่น `kapi`) ไม่เรียกฟังก์ชันภายใน ไม่พึ่งโครง DOM/คลาสของโปรแกรม
- [ ] ไม่อ่าน `ai-key.json` · ไม่อ่าน `localStorage` ของโปรแกรมหรือปลั๊กอินอื่น
- [ ] ไม่เขียนทับไฟล์งานของผู้ใช้ ([6.3](06-data-and-files.md#63-ไฟล์ที่ห้ามเขียนทับ))
- [ ] ไม่ดักการกดแป้นทั้งหน้าต่างเกินกว่าที่ฟีเจอร์ต้องใช้ · ไม่บันทึกสิ่งที่ผู้ใช้พิมพ์

### เครือข่ายและข้อมูลของผู้ใช้

- [ ] **ไม่ส่งอะไรออกนอกเครื่องโดยผู้ใช้ไม่ได้สั่ง** — ไม่มี telemetry · ไม่มี "เช็กอัปเดต" เงียบ ๆ · ไม่มีการโหลดสคริปต์/ฟอนต์/รูปจากเน็ตตอนเริ่ม
- [ ] ถ้าฟีเจอร์ต้องส่งข้อมูล: บอกใน README และในหน้าจอ **ก่อน** ส่งครั้งแรกว่า ส่งอะไร · ไปที่ไหน · เพื่ออะไร — และให้ปิดได้
- [ ] ส่งเท่าที่จำเป็น (ข้อความที่เลือก ไม่ใช่ทั้งฉาก · ทั้งฉาก ไม่ใช่ทั้งเล่ม)
- [ ] ไม่ส่งทางเต็มของไฟล์ ชื่อผู้ใช้ของเครื่อง หรือชื่อผลงาน
- [ ] ใช้ `https://` เสมอ
- [ ] **ไม่ดาวน์โหลดโค้ดมารัน** (`eval` · `new Function` กับข้อความจากเน็ต · `<script src>`) — สิ่งที่ผู้ใช้ตรวจและอนุญาตต้องเป็นสิ่งที่ถูกรัน

### ความลับ

- [ ] คีย์ API/โทเคนที่ผู้ใช้กรอกให้ปลั๊กอิน: เก็บใน `localStorage` เท่านั้น — **ไม่ใช่** `k2.setSettings` (ลงไฟล์ผลงานที่ถูกส่งต่อ) และไม่ใช่ไฟล์ในผลงาน
- [ ] ช่องกรอกความลับใช้ `<input type="password">` (ตัวแสดงปุ่มที่กดของโปรแกรมจะไม่โชว์สิ่งที่พิมพ์ในช่องชนิดนี้)
- [ ] ไม่ `k2.log` ความลับ เนื้อหาของผลงาน หรือ URL ที่มีคีย์ — ผู้ใช้อาจแปะ Log ในรายงานบั๊กสาธารณะ
- [ ] **ไม่มีความลับของคุณเองในซอร์ส** — ไฟล์ปลั๊กอินเป็นข้อความที่ทุกคนอ่านได้ ถ้าต้องมีคีย์ฝั่งเซิร์ฟเวอร์ ให้ทำตัวกลางของคุณเอง

### ข้อความที่ไม่น่าเชื่อถือ

ข้อความจาก **ไฟล์ของผลงาน · เครือข่าย · สิ่งที่ผู้ใช้พิมพ์** เป็นข้อมูล ไม่ใช่โค้ด:

- [ ] ใส่ลงหน้าจอด้วย `textContent` — ไม่ใช่ `innerHTML` / `insertAdjacentHTML` / `outerHTML`
- [ ] `k2.menuPopup`: ใช้ `text:` ไม่ใช่ `label:` (ซึ่งเป็น HTML)
- [ ] ไม่ต่อข้อความพวกนี้ลงใน `style`/`href`/`src` โดยไม่ตรวจ (สี: ตรวจด้วย regex `^#[0-9a-f]{3,8}$` · ลิงก์: รับเฉพาะ `https:`)
- [ ] ไม่ `eval` / `new Function` / `setTimeout("สตริง")` กับข้อความพวกนี้
- [ ] `JSON.parse` ใน `try/catch` · ตรวจชนิดของสิ่งที่ได้ก่อนใช้
- [ ] ทางไฟล์ที่ประกอบจากข้อมูล: ปฏิเสธ `..` และอักขระคั่นทางเอง ก่อนส่งให้ `k2.readFile`/`writeFile`
- [ ] สร้างไฟล์ HTML/Markdown/CSV จากข้อมูลของผู้ใช้: escape ให้ถูกรูปแบบของไฟล์นั้น (HTML: `& < > "` · CSV: ครอบ `"` และระวังเซลล์ที่ขึ้นต้นด้วย `= + - @`)

ทำไมเข้มกว่าเว็บทั่วไป: ช่องโหว่ XSS ในปลั๊กอิน = โค้ดของคนแปลกหน้าได้รันด้วยสิทธิ์เดียวกับปลั๊กอิน (ซึ่งคือสิทธิ์ของโปรแกรม) เพียงเพราะผู้ใช้เปิดผลงานที่มีชื่อฉากประหลาด

### ความเสถียรคือความปลอดภัยของงานเขียน

- [ ] ไม่ทำงานซิงก์ยาว ๆ (ค้างทั้งโปรแกรม = ผู้ใช้บังคับปิด = งานที่ยังไม่บันทึกหาย)
- [ ] `try/catch` รอบงาน async ทุกก้อน · ไม่ปล่อย Promise rejection ลอย
- [ ] เก็บกวาดครบก่อนประกาศ `hotReload` ([4.3](04-hooks-lifecycle.md#43-วงจรชีวิต-และ-hotreload))
- [ ] ทดสอบตอนไม่มีผลงานเปิด · ตอนไม่มีเอกสารเปิด · ตอนเอกสารเป็นหน้า Wiki · ตอนเปลี่ยนผลงาน

## 7.5 สิ่งที่ผู้เขียนควรบอกผู้ใช้ (ใน README)

ผู้ใช้ตัดสินใจจากข้อมูลที่คุณให้ — เขียนให้ตรง:

```markdown
## สิทธิ์และข้อมูล

- **อ่าน**: เนื้อของฉากที่เปิดอยู่ · ไฟล์ทะเบียนของผลงาน (เพื่อนับคำทั้งเล่ม)
- **เขียน**: ไฟล์ `Reports/manuscript-report.md` ในผลงาน (เมื่อกดคำสั่ง "สร้างรายงานต้นฉบับ" เท่านั้น)
- **เครือข่าย**: ไม่ใช้
- **เก็บค่า**: จำนวนคำล่าสุดต่อผลงาน (ใน project.khn.json)
- **ไม่ทำ**: ไม่แก้ไฟล์ฉาก · ไม่ส่งข้อมูลออกนอกเครื่อง
```

## 7.6 รายงานช่องโหว่

- **ของตัวโปรแกรม** (เช่น ทางที่ปลั๊กอินของผลงานถูกรันโดยไม่ได้รับอนุญาต): แจ้งผู้ดูแลโครงการ — ถ้าเป็นเรื่องที่ไม่ควรเปิดเผยก่อนแก้ **อย่าใส่รายละเอียดวิธีโจมตีในรายงานบั๊กจากในโปรแกรม** เพราะรายงานนั้นเป็นสาธารณะ ให้แจ้งสั้น ๆ ว่ามีเรื่องความปลอดภัยและขอช่องทางส่วนตัว
- **ของปลั๊กอินตัวอื่น**: แจ้งผู้เขียนปลั๊กอินนั้นที่รีโปของเขา
- **ของปลั๊กอินคุณเอง**: ออกรุ่นแก้ · เขียนในบันทึกการเปลี่ยนแปลงให้ชัดว่ารุ่นไหนได้รับผลและต้องอัปเดต (ผู้ใช้ต้องติดตั้งทับเอง — ไม่มีการอัปเดตอัตโนมัติ)

## 7.7 ข้อจำกัดที่รู้อยู่ของรุ่นนี้

| เรื่อง | สถานะ |
|---|---|
| แซนด์บ็อกซ์ / สิทธิ์รายความสามารถ | ไม่มี |
| การลงนามปลั๊กอิน / ยืนยันตัวผู้เขียน | ไม่มี |
| การรีวิวจากส่วนกลาง | ไม่มี (ไม่มีร้าน) |
| การตรวจสอบความถูกต้องของไฟล์ที่ติดตั้งจากลิงก์ (checksum) | ไม่มี — พึ่ง HTTPS ของต้นทาง |
| การอนุญาตสำหรับปลั๊กอินของผู้ใช้ที่ไฟล์ถูกแก้ทีหลัง | ไม่มี — ใครเขียนไฟล์ในโฟลเดอร์ข้อมูลผู้ใช้ได้ ก็เปลี่ยนโค้ดที่รันได้ |
| รายการโดเมนที่ปลั๊กอินติดต่อได้ | ไม่มี |
| การตรวจ `entry` ที่ชี้ออกนอกโฟลเดอร์ปลั๊กอิน | เป็นกติกาของ manifest ที่ผู้เขียนต้องทำตาม — อย่าพึ่งให้ตัวโหลดปฏิเสธให้ |
